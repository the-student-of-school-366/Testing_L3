# Нагрузочное тестирование REST API

Эксперимент для занятия «Нагрузочное тестирование». Нагрузка подаётся на локальный сервис этого репозитория, тем же router, что и `cmd/server`. Публичные стенды не использовались.

Прогон выполнен программой на Go (`go run ./cmd/loadtest`): виртуальные пользователи, CSV-параметризация, постоянная пауза, проверка каждого ответа, три уровня нагрузки, файлы JTL и HTML-отчёт. Это тот же протокол эксперимента, что в задании для JMeter. Отдельный `.jmx` не прилагался: измерен именно этот прогон.

## Как повторить

Из корня репозитория:

```bash
go run ./cmd/loadtest
```

Сервер поднимается сам на `127.0.0.1` со свободным портом. Если API уже запущен:

```bash
go run ./cmd/loadtest -base-url http://127.0.0.1:8080
```

Пути к CSV и каталогу результатов ищутся от `go.mod`, править их вручную не нужно. Одиночная итерация (smoke) выполняется до профилей и должна пройти без ошибок.

Повторный запуск перезаписывает `loadtest/results`.

## Сценарий

Один виртуальный пользователь на каждой итерации:

1. `POST /api/v1/auth/login` — HTTP 200, непустой `access_token`, username совпал с CSV.
2. `GET /api/v1/auth/me` — HTTP 200 по Bearer-токену, username и email на месте.
3. `POST /api/v1/posts` — HTTP 201, `id` не пустой, `title` и `user_id` совпали с CSV.
4. `GET /api/v1/posts/{id}` — HTTP 200, тот же id и исходный title.
5. `PATCH /api/v1/posts/{id}` — HTTP 200, title равен `patched_title`.

Неуспешный шаг останавливает итерацию: зависимые запросы не отправляются. В этом прогоне таких остановок не было.

## Параметризация и пауза

Файл `loadtest/data/posts.csv`, 15 строк. Общий для всех пользователей счётчик выдаёт следующую строку на каждую итерацию. В запросах используются поля:

`username`, `password`, `title`, `body`, `user_id`, `patched_title`.

Логин учебного API — `Bret` / `Password@123` (регистр username в CSV разный, сервер принимает его без учёта регистра). Меняются заголовок, текст, `user_id` и новый заголовок.

**Think time: 200 мс перед каждым запросом** (constant timer). При мгновенном ответе это потолок примерно 5 RPS на пользователя: 50, 125 и 250 RPS для 10, 25 и 50 пользователей.

## Профиль нагрузки

Три запуска подряд, один и тот же сценарий и та же пауза. Отличаются число пользователей и ramp-up.

| Запуск | Пользователи | Ramp-up | Время жизни пользователя | Окно полной конкуренции |
|--------|--------------|---------|--------------------------|-------------------------|
| 1 | 10 | 10 с | 25 с | 15 с |
| 2 | 25 | 25 с | 40 с | 15 с |
| 3 | 50 | 50 с | 65 с | 15 с |

Пользователь стартует равномерно в течение ramp-up и затем крутит сценарий `ramp-up + 15 с`. Окно сравнения — 15 секунд после конца ramp-up: к этому моменту активны все пользователи, а первый ещё не остановился. Иначе более длинный ramp-up занизил бы средний RPS и запуски было бы не с чем сравнивать.

Слушатели вроде View Results Tree нет. Каждый запрос пишется в JTL, агрегаты считаются после прогона.

## Результаты

Точные метрики — `loadtest/results/summary.json` и `loadtest/results/report/index.html`. JTL хранит elapsed целыми миллисекундами, поэтому субмиллисекундные ответы там выглядят как 0 или 1. В таблице ниже время из точного замера.

Установившееся окно 15 с:

| Нагрузка | Throughput / RPS | Average | Median | p95 | Error Rate |
|----------|------------------|---------|--------|-----|------------|
| 10 users, ramp-up 10 с | 50.0 | 0.496 мс | 0.505 мс | 1.577 мс | 0% |
| 25 users, ramp-up 25 с | 124.7 | 0.464 мс | 0.523 мс | 1.180 мс | 0% |
| 50 users, ramp-up 50 с | 248.9 | 0.231 мс | 0.000 мс | 0.759 мс | 0% |

Весь запуск, включая ramp-up и хвост, когда часть пользователей уже остановилась:

| Нагрузка | Wall | Samples | RPS | Average | p95 | Error Rate |
|----------|------|---------|-----|---------|-----|------------|
| 10 users | 34.2 с | 1250 | 36.6 | 0.449 мс | 1.283 мс | 0% |
| 25 users | 64.2 с | 5000 | 77.8 | 0.431 мс | 1.109 мс | 0% |
| 50 users | 114.5 с | 16250 | 141.9 | 0.340 мс | 1.047 мс | 0% |

Файлы прогона:

- `loadtest/results/10-users.jtl`
- `loadtest/results/25-users.jtl`
- `loadtest/results/50-users.jtl`
- `loadtest/results/summary.json`
- `loadtest/results/report/index.html`

## Вывод

Throughput в установившемся окне вырос с 50.0 до 248.9 RPS, то есть в 4.98 раза при росте числа пользователей в 5 раз. Это почти потолок паузы 200 мс (50 / 125 / 250 RPS). Сервис успевал отвечать так быстро, что интенсивность задавала пауза пользователя, а не очередь на API.

Среднее время осталось около 0.2–0.5 мс, p95 — около 0.8–1.6 мс. Медиана на 50 пользователях равна 0 мс: не меньше половины ответов короче шага таймера и записаны как нулевые. Среднее 0.231 мс и p95 0.759 мс остаются в том же субмиллисекундном диапазоне. Это шум измерения на localhost, а не ускорение и не деградация.

Ошибок не было ни на одном уровне (error rate 0%). Момент, когда throughput перестаёт расти, а latency или error rate начинают увеличиваться, в выбранном диапазоне не наступил.

Стабильным можно считать весь исследованный диапазон: 10, 25 и 50 виртуальных пользователей. До отказа сервис не доводился.
